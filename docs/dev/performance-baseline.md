# 性能基线（本机）

> 固化「大目录加载耗时 + 内存」的本机基准，改了加载 / 缓存 / 布局相关的代码后有数字可比。**只作本机对比，不进 CI**（原因见[文末](#为什么不进-ci)）。命令入口见 [build.md](build.md#性能基线本机)。

## 怎么用

```bash
scripts/bench/run.sh --dry-run     # 只打印计划
scripts/bench/run.sh               # 300 / 6000 / 20000 三档，约 2.5 分钟，输出 Markdown 表
scripts/bench/run.sh 6000          # 只跑一档
```

- 前提：Debug 版已构建到 `.build/DerivedData-root`（产物 `PixyDbg`；构建命令见 build.md）。Release 构建没有日志写文件的开关（`PIXY_LOG_FILE` 只在 `#if DEBUG` 里），所以基线只能是 Debug 对 Debug；Debug 未优化，绝对数字比 Release 慢，只看相对变化。
- **改动前后各跑一次**（建议各跑两次），在**同样的屏幕状态与后台负载**下对比，判定规则见[如何对比](#如何对比)。
- 运行时会在屏幕上出现 PixyDbg 窗口，别操作它；也别同时跑别的重负载；已有 PixyDbg 在运行时脚本会拒绝（避免杀掉你正在看的实例）。

后果与处理：

- 脚本会在开头警告并把屏幕状态（`亮屏 / 熄屏`、`已锁定 / 未锁定`）写进报告抬头；**只有「亮屏、未锁定」的结果能互相比较**。
- **本次基线是在熄屏状态下取得的**（需要无人值守地跑完，没有办法解锁），所以它只能和同样熄屏的运行对比。有人在场时，请在亮屏、解锁的状态下连续跑两次，把结果补进上面的表（并保留熄屏这一组），以后日常对比用亮屏的那组。
- 锁屏标志（`CGSSessionScreenIsLocked`）读自 `ioreg`，在熄屏期间的读数并不稳定（同一次熄屏期间观察到过 `已锁定` 与 `未锁定` 两种读数），显示器是否休眠才是更可靠的判据。

## 测量定义

**耗时**：全部来自应用日志里已有的 `log("Time taken to …: <秒> seconds")`（`PIXY_LOG_FILE` 把它们写进文件，脚本按文案精确匹配，取第一次格式正确的出现）。基准点都是同一个 `startTime`，在 `FileSystem.swift` 的 `switchDirByDirection` 开头设置（每次切换目录重设），用的是 `DispatchTime` 的单调时钟，不含系统睡眠时间。

| 列 | 日志文案（`Time taken to …`） | 打印的位置 | 含义 |
|---|---|---|---|
| 文件列表 | `complete file list` | `FileSystem.swift`，`treeTraversal` 之后 | 扫描目录、写好 `DirModel`（排序键、过滤） |
| 首图 | `complete loading first image` | `ViewController.swift`，缩略图线程 | 第一张缩略图解码完成并交回 |
| **尺寸信息读完** | `fully load size information` | `ViewController.swift`，readInfo 回主线程处理完最后一个文件（`i == count-1`） | **主指标**：全部文件的尺寸读完、布局算完。脚本以它出现作为「加载完成」，120 秒内不出现记 FAIL |
| 缩略图读完 | `fully load image thumbnails` | `ViewController.swift`，缩略图线程取到**最后一个文件**的任务时 | 辅助列，不参与判定 |

「缩略图读完」在 6000 与 20000 档没有：readInfo 循环只把前 `globalVar.memUseLimit`（默认 4000）个文件的缩略图任务推进队列，更靠后的要等滚动才会加载，所以最后一个文件的任务从不触发。后果是 6000 与 20000 档**实际都只解码 4000 张缩略图**，它们的内存差异主要来自逐文件的模型与布局缓存，而不是缩略图。

**RSS**：`ps -o rss= -p <pid>`，每 0.5 秒一次（加上 `ps` 自身开销，实际约 0.55 秒），从启动后立即开始。**峰值** = 全程样本的最大值（采样最大值，会漏掉比 0.5 秒短的尖峰）；**稳态** = 观察窗口末尾 5 个样本的中位数。第一个样本可能是 `exec` 之前的子 shell（约 0 MB），对峰值与中位数都没有影响。

**观察窗口**：从第一次轮询到「尺寸信息读完」那行起，再观察 40 秒（整数秒计时，实际 40–41 秒，不会更短）。选 40 秒是因为 RSS 在加载完之后还要持续回落：实测大目录要到启动后 15–30 秒才落到平台（见下表），窗口太短会把「还没回落」当成稳态。可用 `PIXY_BENCH_SETTLE` 调整。

| 启动后 | 5 秒 | 10 秒 | 15 秒 | 20 秒 | 25 秒 | 30 秒 | 40 秒 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 6000 档 RSS（基线 1） | 342 | 305 | 117 | 93 | 69 | 64 | 62 |
| 20000 档 RSS（基线 1） | 302 | 482 | 367 | 296 | 145 | 117 | 62 |
| 20000 档 RSS（基线 2） | 300 | 472 | 364 | 278 | 109 | 60 | 61 |

**footprint**：窗口结束时调一次 `footprint --noCategories -f bytes -p <pid>`（最多等 10 秒），取 `phys_footprint`（当前值，列「稳态 footprint」）与 `phys_footprint_peak`（内核记录的整个进程生命周期峰值，列「峰值 footprint」，不依赖采样，不会漏尖峰）。它和活动监视器的「内存」列同口径，含被系统压缩的页。

### RSS 与 footprint

两者差很多，且 RSS 稳态不能用于对比：

- RSS 只统计常驻在物理内存里的页。进程在后台、闲置时系统会把它的页压缩 / 换出，RSS 就掉下去，**但内存并没有被应用释放**：同一次运行里 6000 档 RSS 从 380 MB 掉到 55 MB 的同时，footprint 一直是 227 MB 不变（手动对照过，`footprint` 的 `phys_footprint` 在 t=8/16/22/28/34/44 秒分别是 218/225/227/227/227/227 MB）。
- 回落发生的时间并不固定：300 档在基线 1 里启动后约 15 秒就回落到 90 MB，在基线 2 里 40 秒后仍停在 182 MB，所以 300 档「稳态 RSS」是 90 与 185 两个值之间的二选一（6 次运行里是 90.7、181.9、197.3、187.0、89.8、182.3）。
- RSS 还包含共享库 / 映射文件的页（dyld 共享缓存、Debug 构建的 `PixyDbg.debug.dylib` 等），所以 300 档 RSS 峰值（约 190 MB）远大于 footprint 峰值（约 74 MB）。
- 结论：**耗时看表里的耗时列，内存看 footprint 两列**；RSS 两列只作旁证（峰值 RSS 作为粗略的采样峰值，6 次里 180–213 / 383–509 / 564–620 MB）。

## 噪声与注意事项

- **屏幕状态**：最大的单项影响，见上。
- **系统睡眠**：测量中途系统睡眠会让 RSS 观察窗口作废（实测遇到过「用户离开后整机睡眠」和「接电源时的维护睡眠」各一次）。脚本运行期间用 `caffeinate -dis` 阻止显示器熄屏、空闲睡眠和接电源时的系统睡眠（后者需要连接电源）；它不会把已经熄灭的显示器点亮。
- **后台负载**：Parallels 虚拟机、OrbStack、`mediaanalysisd` / `mds_stores` 等系统任务会和测量抢 CPU，大目录（20000 档）对 CPU 最敏感，这也是它「文件列表」6 次里波动 5.9% 的主要原因。对比前后要在相近的负载下跑。
- **冷 / 热缓存**：
  - 应用**没有落盘的缩略图缓存**（代码里没有磁盘缓存，`Application Support/Pixy` 与 `~/Library/Caches` 下都没有产生任何文件），所以第二次运行不会被应用自己的缓存加速；每次启动都是空的进程内缓存。
  - 系统的**文件页缓存是热的**：脚本每次都是刚把种子图写盘再启动，PNG 在页缓存里；冷读取（需要 `purge`，要 root）没有测。20000 档的目录用硬链接指向 300 个 inode，页缓存也只需要装 300 个文件的内容。
  - 观察到的两次连续运行（基线 1 → 2）没有「第一次慢、第二次快」的迹象（耗时差异 ≤ 1%），6 次运行里也没有随次序单调变化的趋势。
- **硬链接的副本**共享同一个 inode，大小、修改日期、内容完全一致；真实目录比这杂得多（日期各异、文件大小分布宽、有 RAW / 视频 / 子目录）。所以数字反映的是「读尺寸 + 布局 + 解码 4000 张缩略图」的管线开销，不代表真实相册的绝对耗时。
- **图片内容**：`scripts/bench/gen-images.py` 生成 300 张确定性的 PNG（长边 1200 px，8 种宽高比循环，文件名 `img_%05d.png`），同一台机器每次得到完全相同的文件集合。
- **Debug 构建的内存监视线程**：`#if DEBUG` 下 `memMonitorThread` 在目录 LRU 队列 ≥ 2 项时会每 2 秒主动清缩略图来复现问题；基线里只打开一个目录，队列只有 1 项，不会触发（日志里没有 `Memory free:`）。

## 如何对比

1. 改动前跑一次（建议两次）：`scripts/bench/run.sh | tee /tmp/before.md`；改动后重建 Debug 再跑一次或两次，`tee /tmp/after.md`。
2. 屏幕状态、后台负载保持一致：两份报告抬头里的「屏幕」必须相同。
3. 判定规则（来自上面 6 次运行的波动，连续两次运行的差异 ≤ 1%）：
   - **耗时**（首图、尺寸信息读完、缩略图读完）：差异 **< 5%** 视为噪声；**≥ 10%** 视为真实变化，重跑一次确认。小目录的「文件列表」只有 0.04–0.05 秒，以 ±0.01 秒为噪声。
   - **内存**：只看 footprint；差异 **< 10%** 视为噪声（峰值波动 ≤ 4%，稳态 ≤ 8%）。RSS 稳态不用于对比。
   - 一般化的说法：只有当改动前后的差异**大于两次连续运行差异的约 5 倍**（且超过上面的百分比下限）时才下结论。
4. 想判断是「首个界面出现」还是「全部读完」变慢：看「首图」与「尺寸信息读完」两列；想判断是扫描目录变慢：看「文件列表」。

## 为什么不进 CI

- macOS runner 配额紧张，已经因此在排队约 15 分钟后以 `The job was not acquired` 失败过（见 [build.md](build.md#公开发布签名公证和产物)），再加一个要跑几分钟的任务只会雪上加霜；
- GitHub 的 macOS runner 是虚拟机，CPU 与磁盘被共享，数字抖动远大于要检测的变化，得到的只会是时灵时不灵的误报；
- 屏幕状态是本基线最敏感的限定条件，而 runner 上没有可用的显示器与登录会话；
- 基线需要和同一台机器上的历史数字比，不是一个绝对阈值。
